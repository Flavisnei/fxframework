Instalar o gerenciador

fx-modules depende apenas de fx-core. O núcleo mínimo continua sem gerenciador, HTTP, banco ou templates. Para usar os comandos, instale também fx-console. Na distribuição completa, ambos já estão incluídos.

php vendor/bin/fxartisan module:install modules --constraint=@dev

Durante o desenvolvimento local, o composer.json consumidor precisa de repositório path apontando para os pacotes do framework, minimum-stability dev e prefer-stable true. Os pacotes ainda não foram publicados. Depois da instalação, execute o Artisan novamente. Compatibilidade de PHP e versões de pacotes pertence ao require do Composer; requires do manifesto abaixo expressa dependências de ativação por identificador, sem interpretar restrições de versão.

Declarar um módulo

Crie um fx-module.json junto ao código do módulo. Registre seu provider no autoload PSR-4 do Composer e gere o autoload. Cada módulo precisa de um provider próprio, que estenda ServiceProvider, e de ajuda HTML existente.

{
  "schema": 1,
  "id": "contacts",
  "version": "1.0.0",
  "provider": "App\\Modules\\ContactsProvider",
  "requires": [],
  "help": "docs/index.html",
  "permissions": ["contacts.read"]
}

Campos obrigatórios: schema 1, id, version, provider e help. IDs usam letras minúsculas, números, hífens e pontos entre segmentos. Versão usa três números e pode incluir sufixo de pré-release/build. Alterações no comportamento do módulo devem aumentar sua versão e atualizar a ajuda. Campos desconhecidos são rejeitados para detectar erros de digitação.

Campos opcionais: requires (lista de IDs), permissions (lista de identificadores), assets e migrations (diretórios relativos), routes (objeto com contextos http, wordpress ou console apontando para arquivos relativos). Os recursos precisam existir e permanecer dentro da pasta real do módulo, inclusive após resolver symlinks. A ajuda deve ter extensão .html.

Esses recursos são metadados. O gerenciador não executa arquivos de rotas, migrations, publica assets nem concede permissões. O provider integra o contexto desejado explicitamente; permissões precisam ser verificadas no servidor pelo sistema de autorização. O painel que usará esses metadados ainda está planejado.

Registrar na aplicação

Crie config/modules.json na aplicação:

{
  "schema": 1,
  "manifests": ["modules/contacts/fx-module.json"]
}

Para um módulo distribuído via Composer, use um caminho como vendor/minhaempresa/contacts/fx-module.json. Os caminhos são relativos à aplicação; não são aceitos caminhos absolutos ou segmentos .. nesta lista. Symlinks de repositórios path são aceitos porque o destino foi explicitamente registrado. Não há varredura automática de vendor ou execução de manifestos PHP.

Dois módulos não podem compartilhar o mesmo ID ou provider. A configuração ausente representa catálogo vazio. Um manifesto listado, mas ausente ou inválido, interrompe a validação; corrija a configuração, sem ocultar a falha.

Ativar, consultar e desativar

php vendor/bin/fxartisan module:status
php vendor/bin/fxartisan module:enable contacts
php vendor/bin/fxartisan module:doctor
php vendor/bin/fxartisan module:disable contacts

enable ativa também as dependências registradas, em ordem. Não baixa dependências que ainda não estejam instaladas e registradas. A validação rejeita ciclos, dependências ausentes, providers inválidos e recursos inexistentes. As classes dos providers são verificadas pelo autoload, mas seus construtores/register/boot não são chamados pelos comandos.

disable é bloqueado quando outro módulo ativo depende diretamente dele; desative primeiro os dependentes. A operação preserva código, dados, assets e permissões existentes. status mostra versões disponíveis e reconhecidas, incluindo IDs ativos que saíram do catálogo. doctor valida o conjunto ativo, não garante que o código de cada provider funcione em execução.

module:list continua sendo o catálogo de componentes instaláveis do framework. module:status é a consulta dos módulos de negócio registrados pela aplicação.

Carregar os módulos ativos

No bootstrap, após configurar serviços do ambiente e antes de boot():

$app = new Fx\Framework\Foundation\CoreApplication(__DIR__);
$modules = new Fx\Framework\Modules\ModuleManager(__DIR__);
$modules->register($app);
$app->boot();

Em uma aplicação HTTP, use sua Application já existente. No WordPress, use o CoreApplication retornado por Plugin::app(), no hook apropriado e antes de boot(). Não crie um segundo kernel. O gerenciador valida o conjunto ativo inteiro antes de registrar providers, depois registra dependências primeiro. Exceções dentro do código de um provider interrompem o bootstrap; seus efeitos anteriores não têm rollback automático.

Mudanças de ativação valem no próximo bootstrap. Reinicie workers persistentes após alterações. Registrar depois de boot() é rejeitado. O carregamento de um processo existente não é desfeito pela desativação.

Atualizar um módulo

  1. Prepare o deploy com cópia do lock, estado e dados; revise as instruções da ajuda do módulo. Faça a troca de código em janela controlada, com workers parados.
  2. Atualize o pacote pelo Composer no projeto consumidor, por exemplo composer update minhaempresa/contacts. Use as restrições e políticas do projeto. module:refresh não baixa código.
  3. Execute module:doctor. Uma versão diferente da reconhecida bloqueia o carregamento até a revisão. Registre novas dependências no catálogo e ative-as explicitamente com module:enable ID, se a atualização exigir.
  4. Execute os passos de migration/configuração indicados pelo módulo e, então, module:refresh e module:doctor. refresh valida o grafo e providers, reconhece as versões disponíveis de todos os módulos ativos e não ativa dependências novas.
  5. Reinicie os processos e confira o funcionamento antes de liberar tráfego.

enable preserva a versão anteriormente reconhecida dos módulos que já estavam ativos, permitindo preparar novas dependências sem aprovar silenciosamente uma atualização. Se a atualização falhar, restaure código, lock, estado e dados conforme o procedimento de deploy do projeto. O gerenciador não oferece rollback de banco nem detecta mudanças feitas sem alterar a versão do manifesto.

Estado e problemas comuns

O arquivo storage/framework/modules.json guarda somente os IDs ativos e as versões reconhecidas. É separado do código e deve ser preservado entre deploys, com backup. Não edite durante operações concorrentes. Escritas usam lock exclusivo e substituição por arquivo temporário no mesmo diretório; o bootstrap apenas lê. JSON corrompido causa erro, nunca desativação silenciosa de todos os módulos.

O usuário do CLI precisa escrever em storage/framework, e o usuário da aplicação precisa ler o estado. Em Unix o arquivo novo usa permissão 0660; configure grupo e acesso aos diretórios. Estado não contém segredos. Não execute comandos de administração por uma rota pública.

Provider ausente: revise namespace e autoload do consumidor, execute composer dump-autoload. Dependência desativada: instale, registre e habilite o ID informado. Pacote removido: restaure-o ou retire seu caminho da configuração e desative o ID, começando pelos dependentes. Ajuda/recurso inválido: corrija o caminho relativo. Estado corrompido: restaure uma cópia válida. Não apague o estado para mascarar o erro.

O lock coordena comandos que usam este gerenciador, não edições manuais ou Composer. Não há lock distribuído; para múltiplos servidores, distribua estado e código de maneira coordenada. Validação funcional realizada em Windows/PHP 8.1.12; filesystem distribuído e execução Unix ainda não testados.
