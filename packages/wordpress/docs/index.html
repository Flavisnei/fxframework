1. Preparar o plugin

O pacote fxfavalessa/fx-wordpress exige PHP ^8.1 e FX Core. O WordPress é fornecido pelo site, não pelo Composer. O adaptador não instala kernel HTTP do FX, Eloquent, Smarty nem login próprio.

No checkout do framework:

composer install --working-dir=examples/wordpress --no-dev

Copie a pasta examples/wordpress completa, incluindo vendor, para wp-content/plugins/fx-example em um site de desenvolvimento. Ative FX Example e abra Configurações → FX Example. Preencha o nome e clique em Salvar: a página envia JSON para a REST API e mostra o resultado sem recarregar.

Execute Composer antes de copiar: o manifesto do exemplo aponta para ../../packages/* dentro deste repositório. Para um plugin próprio, configure o caminho absoluto ou relativo ao checkout em repositories do projeto consumidor. Use requisito fxfavalessa/fx-wordpress @dev, minimum-stability dev e prefer-stable true durante desenvolvimento local.

Se vendor estiver ausente, o plugin mostra um aviso administrativo. O pacote ainda não foi publicado e não há instalador de módulos no Artisan.

2. Integrar recursos nativos

add_action('plugins_loaded', function () {
    $plugin = new Fx\Framework\WordPress\Plugin(__FILE__, 'meu-plugin');
    $plugin->app()->boot();
    $plugin->rest('/status', 'GET',
        fn () => ['ok' => true],
        $plugin->permission('manage_options')
    );
});

O endpoint será /wp-json/meu-plugin/v1/status. Registre providers antes de app()->boot(). Cada instância tem seu CoreApplication e configuração. Escolha um slug único; duas instâncias com o mesmo slug compartilham o namespace REST e o prefixo de opções.

action e filter delegam hooks, prioridade e número de argumentos ao WordPress. rest registra no rest_api_init e exige um permission_callback explícito. Os callbacks recebem WP_REST_Request e devolvem os formatos nativos: arrays, WP_REST_Response ou WP_Error.

user() consulta o usuário atual sem cache; can() e permission() usam current_user_can, incluindo argumentos de permissões por objeto. database() devolve o mesmo wpdb global do site, sem abrir conexão. Em SQL próprio, use wpdb::prepare e as tabelas/prefixos do host.

option('name', '') e updateOption('name', $valor) usam um nome prefixado pelo slug. updateOption retorna false tanto quando nada mudou quanto em certas falhas, seguindo update_option. Esses métodos não fazem autorização ou sanitização: valide e autorize antes, como no exemplo.

3. AJAX, usuário e permissões

O formulário de exemplo requer manage_options tanto na página quanto no endpoint. O WordPress valida o tipo e tamanho do campo; a sanitização remove marcação e rejeita texto vazio. A opção é gravada pela API nativa.

O JavaScript só carrega nessa página administrativa. Ele envia Content-Type application/json, cookies da mesma origem e X-WP-Nonce gerado com wp_create_nonce('wp_rest'). Trate falhas de rede, sessão expirada e respostas de erro. Não use o token CSRF do FX nem crie uma sessão PHP para essa integração.

O nonce não substitui permissões. A autenticação por cookie e a verificação do nonce são realizadas pelo WordPress, inclusive o tratamento de usuário anônimo quando o nonce falta. APIs com senhas de aplicação usam o mecanismo nativo correspondente.

Referências: autenticação REST, capabilities, endpoints.

4. Coexistência e limites

O adaptador não substitui o container global do Illuminate, não inicia sessão PHP, não intercepta o roteador do site e não altera a conexão global wpdb. A configuração é isolada por instância e os dados do exemplo por slug.

Isso não isola versões diferentes de bibliotecas PHP carregadas por outros plugins. Para distribuição ampla, ainda será necessário definir prefixação de dependências ou uma versão compartilhada compatível. Foram aprovadas 28 verificações reais em WordPress 6.4.3 com PHP 8.1.12 e MariaDB 10.4.27 temporário; não presume compatibilidade com todos os plugins, multisite ou versões do WordPress.

O exemplo não adiciona usuários, roles, tabelas ou login próprio. Desativá-lo preserva sua opção fx-example:name; não há rotina automática de exclusão de dados. O painel completo FX Windows continua em outra etapa.

Erros comuns

404: confira ativação, slug e registro no hook correto. 401/403: confira usuário, capability e nonce, recarregando a página após nova autenticação. 400: campo inválido. Classe ausente: confira vendor/autoload.php do plugin. Inicialização fora do WordPress gera uma mensagem explícita.

Homologação multisite e outros plugins

O adaptador usa as opções e permissões do site atual. Ao usar switch_to_blog, finalize com restore_current_blog em finally. As opções possuem prefixo do plugin; usuários e capacidades continuam sob controle do WordPress. Não use o mesmo slug para dois plugins independentes.

No repositório, tests/integration/wordpress-matrix.py prepara WordPress descartável e permite --multisite e --host-autoload. Instale o vendor do exemplo, informe o PHAR oficial do WP-CLI e uma versão exata; consulte a ajuda central para os comandos. O runner bloqueia email, verifica checksums e remove seu banco temporário. Falha de download ou checksum impede a homologação.

Namespaces PHP são globais: coexistência de containers não resolve automaticamente duas versões incompatíveis da mesma classe. Harmonize as dependências ou distribua os plugins com namespaces isolados; essa transformação não é feita pelo FX. Os resultados da matriz se limitam às combinações testadas.
