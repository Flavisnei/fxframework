Admin e Contatos com MariaDB

Disponível nesta etapa: Admin 0.1.3 e Contatos 0.1.1 aceitam PDO mysql com tabelas InnoDB. Login, usuários, perfis, limites de tentativa, tokens e fila cifrada usam o banco configurado. SQLite continua sendo o padrão e conserva seu schema. Nenhuma dependência foi adicionada ao Core.

Configuração e requisitos

Requer PHP com pdo_mysql e banco MariaDB previamente criado em utf8mb4. O teste local utiliza MariaDB 10.4.27; outras versões precisam ser homologadas. Em config/admin.php, substitua apenas database pela configuração abaixo, preservando secure_cookie, permissões e demais opções:

'database' => [
 'driver' => 'mysql',
 'host' => '127.0.0.1',
 'port' => 3306,
 'name' => 'seu_banco',
 'username' => getenv('FX_DB_USER') ?: 'root',
 'password' => getenv('FX_DB_PASSWORD') ?: '',
],

Root com senha vazia serve somente ao ambiente local autorizado. Para implantação, utilize uma conta própria com os acessos necessários. Não coloque credenciais no Git. AdminConfig::connection(config, create=false) é uma API nova e opcional; database como caminho SQLite absoluto permanece válido.

Para Contatos, crie config/contacts.php retornando ['database' => ...] com a mesma configuração ou outro banco MariaDB. Sem esse arquivo, Contatos mantém storage/contacts.sqlite. Use ContactStore::configured(root, create=false) para a conexão configurada.

Instalar e atualizar

Atualize o vendor do consumidor e execute admin:init para uma base nova; contacts:init cria a tabela sem apagar registros. Execute admin:mail --init se utilizar a fila. Ative os módulos e reconheça as versões com module:refresh após revisar a atualização. Reinicie processos longos. A inicialização HTTP não cria schema.

Migração: mudar a configuração não copia dados de SQLite para MariaDB. Esta etapa atende bases MariaDB novas e preserva bases SQLite existentes. Para migrar dados reais, mantenha backup e planeje transferência validada de IDs, perfis, hashes de senha e referências; não há importador automático nesta versão. Retorno exige restaurar configuração e vendor compatíveis com o banco de origem.

Transações e comportamento

DDL MariaDB executa commit implícito; a criação de tabelas ocorre antes da transação da primeira conta. Uma falha pode deixar tabelas vazias, e a inicialização pode ser repetida. Uma conta existente nunca é substituída. Operações críticas do Admin usam uma linha de bloqueio InnoDB por banco; isso preserva o último administrador, consumo único de token e contador de tentativas. A fila possui bloqueio próprio, liberado antes do transporte SMTP. Esses bloqueios podem limitar vazão sob alta concorrência.

Contatos mantém atualização/exclusão por versão e erro 409 em dados obsoletos. Tabelas novas usam utf8mb4_bin para unicidade sensível a maiúsculas; emails são normalizados pela aplicação. A busca LIKE pode ter diferenças de acentos/maiúsculas em relação ao SQLite. Nenhuma alteração de senha ou envio de email real é feita pela homologação.

Instalação passo a passo

Requisitos: PHP ^8.1, PDO com pdo_sqlite, Composer 2 e sessões PHP. Este primeiro backend usa SQLite diretamente, sem Eloquent ou Smarty. O núcleo mínimo não exige Admin. A distribuição completa passa a exigir as extensões PDO/SQLite; consumidores que não as têm devem habilitá-las ou escolher os pacotes modulares.

No repositório, entre em examples/admin e execute:

composer install
php vendor/bin/fxartisan admin:init --email=seu-email@example.com
php vendor/bin/fxartisan module:enable fx-admin
php -S 127.0.0.1:8080 -t public public/index.php

A senha inicial é solicitada sem exibição. Não há senha padrão. Use 12 a 72 bytes. Abra http://127.0.0.1:8080/admin. O servidor PHP acima é somente de desenvolvimento; a raiz pública é public, nunca a pasta do projeto. Banco, configuração e logs ficam fora de public.

Em outro projeto, adicione os pacotes com php vendor/bin/fxartisan preset:install admin --constraint=@dev. O preset instala Admin e Console com dependências, mas não copia configurações ou cria contas. Copie e adapte config/admin.php, config/modules.json, bootstrap.php e public/index.php do exemplo. Para pacote local use repositories path, minimum-stability dev e prefer-stable true. Não existem releases publicadas ainda.

admin:init lê config/admin.php, cria tabelas e a primeira conta. Repetir o comando não redefine contas existentes. Para execução automatizada, --password-env=FX_ADMIN_INITIAL_PASSWORD lê a senha dessa variável de ambiente; remova-a após instalar. Não coloque a senha nos argumentos do terminal. O comando apenas inicializa o banco, sem ativar o módulo.

No bootstrap, vincule Panel::class a AdminConfig::panel($root) antes de ModuleManager::register($app). O provider fx-admin registra suas rotas. O módulo precisa estar ativo. O prefixo desta versão é fixo: /admin.

Entrar, sair e sessão

O formulário envia JSON com token CSRF; a identidade fica em cookie de sessão HttpOnly e SameSite=Lax. Secure é true por padrão. O exemplo define false exclusivamente para HTTP local; altere para true em HTTPS. Atrás de proxy, configure HTTPS no servidor, sem confiar em cabeçalhos arbitrários do cliente.

AdminConfig usa um nome de sessão derivado da raiz da aplicação para separar instalações. Em deploys com diretórios diferentes a cada release, configure session_name estável e único para a aplicação. Ao instanciar AdminSession diretamente, forneça nome próprio se hospedar mais de um painel no mesmo domínio.

Login e logout renovam o ID da sessão e CSRF. Expiração padrão: 30 minutos sem atividade ou 8 horas totais. Mudanças na conta invalidam sessões anteriores; permissões do perfil são consultadas novamente no servidor. Os dados não são guardados em localStorage. Não há opção “lembrar-me” nesta versão.

Limite por janela de 15 minutos: 10 tentativas de login por email e 50 por IP, incluindo tentativas bem-sucedidas. Excesso retorna 429. O IP vem de REMOTE_ADDR; um proxy pode compartilhar esse IP entre usuários. Ajustes de política e limitador distribuído são trabalhos futuros.

Usuários

Abra Usuários para pesquisar nome/email e navegar por páginas de até 20 registros. Novo usuário permite definir nome, email, senha, perfil e estado ativo. Editar permite alterar esses campos; senha vazia mantém a atual. Os valores são validados pelo servidor e senhas recebem hash.

Desative uma conta para impedir novos acessos e invalidar sua sessão na próxima requisição. Não há exclusão definitiva pelo painel. É proibido desativar ou retirar o perfil do último administrador ativo. Alterações na própria conta exigem novo login.

users.view permite listar; users.manage permite criar, modificar e redefinir credenciais de contas comuns. Somente membros do perfil reservado Administrador podem atribuir esse perfil ou alterar credenciais de administradores, inclusive inativos. Trate users.manage como privilégio administrativo, pois ele controla credenciais de outras pessoas.

Perfis e permissões

Um usuário possui um perfil. Crie um perfil, marque as permissões necessárias e atribua-o ao usuário. O perfil Administrador é reservado e não pode ser alterado. Perfis comuns podem ser modificados; não há exclusão de perfis nesta versão.

PermissãoUso
dashboard.viewBase de acesso e consulta dos perfis para formulários.
users.viewListagem paginada de contas.
users.manageCriação e alteração de contas comuns.
roles.manageCriação e alteração de perfis, inclusive concessão de permissões administrativas.
modules.viewConsulta dos módulos registrados.
modules.manageAtivação e desativação de módulos registrados.

Para operar os formulários de usuários, atribua dashboard.view, users.view e, se necessário, users.manage. Para perfis, atribua também roles.manage. Negação é padrão no servidor; esconder um botão não substitui a autorização. Permissões administrativas podem delegar outros privilégios, portanto atribua-as somente a responsáveis autorizados.

Módulos

A janela mostra os manifestos registrados em config/modules.json e seu estado. A ativação inclui dependências já registradas; não faz downloads. A desativação preserva dados e é bloqueada quando houver dependentes ativos.

O próprio fx-admin é administrado pelo CLI para evitar remover o painel durante uma operação. Atualizações e diagnósticos detalhados continuam no CLI: module:doctor e module:refresh. Reinicie workers persistentes após mudanças. O usuário do servidor precisa escrever no estado para ações pelo painel; conceda modules.manage somente a administradores de confiança.

Recuperar senha

A funcionalidade precisa de integração de entrega. config/admin.php aceita reset_delivery como Closure que recebe (string $email, string $token). Enfileire uma mensagem contendo uma URL HTTPS da sua aplicação, construída a partir de uma origem configurada, nunca do Host enviado pelo cliente:

https://seu-dominio/admin#reset=TOKEN

O fragmento é lido pelo formulário e removido da barra de endereço; o token é enviado somente na solicitação JSON de redefinição. O endpoint não devolve tokens. Armazenamento mantém apenas hash SHA-256 do token aleatório de 32 bytes, validade de 30 minutos e uso único. Nova solicitação substitui o token anterior. Redefinir senha invalida sessões existentes e não efetua login automático.

Com reset_delivery null, a opção fica oculta; não há envio de email configurado no exemplo. A resposta de solicitação é genérica para contas existentes ou ausentes. A entrega deve ser enfileirada para reduzir diferenças de tempo e não bloquear HTTP. Falhas de entrega são registradas sem revelar a existência da conta.

Limites em 15 minutos: 3 solicitações por email, 20 por IP e 20 tentativas de redefinição por IP. Configure e teste o provedor de email antes de disponibilizar recuperação. Os testes do framework usam um callback em memória; nenhuma mensagem real foi enviada.

SMTP com fila local cifrada — Admin 0.1.1

A integração é opcional. Instale composer require symfony/mailer:^6.4 no projeto consumidor. OpenSSL com AES-256-GCM é necessário para a fila. Não adicionamos Mailer ao núcleo nem às dependências obrigatórias do Admin.

O exemplo carrega config/mail.php somente quando FX_MAIL_ENABLED=1. Configure variáveis reais do ambiente do PHP e do trabalhador; o framework não lê .env automaticamente. No exemplo Admin, config/mail.local.json pode fornecer dsn, from, admin_url e key como alternativa local. Esse arquivo é excluído do Git; valores não vazios do ambiente têm prioridade. Mantenha-o fora de public e restrinja sua leitura ao usuário da aplicação. Isso não ativa o envio: FX_MAIL_ENABLED=1 continua necessário:

FX_MAIL_ENABLED=1
FX_MAIL_DSN=smtps://USUARIO:SENHA_CODIFICADOS@HOST:465
FX_MAIL_FROM=remetente@example.com
FX_ADMIN_URL=https://seu-dominio/admin
FX_MAIL_KEY=CHAVE_ALEATORIA_DE_64_CARACTERES_HEXADECIMAIS

Codifique usuário e senha com rawurlencode antes de formar a DSN. Guarde credenciais e chave em um gerenciador de segredos/configuração privada, nunca no Git. Gere a chave uma única vez a partir de random_bytes(32), convertida para hexadecimal; não gere uma chave nova a cada requisição. Preserve-a enquanto houver mensagens pendentes.

Esta versão usa TLS implícito (smtps), com verificação de certificado. Não aceita opções que desabilitam TLS/verificação. Porta 465 é um exemplo, não uma confirmação das configurações do seu provedor. STARTTLS obrigatório na porta 587 ainda não foi implementado. O modo local_test aceita SMTP simples somente em 127.0.0.1 ou ::1, sem autenticação, para capturadores de teste.

  1. Instale as dependências opcionais e prepare as variáveis, incluindo origem HTTPS fixa. Não construa links a partir do Host do cliente.
  2. Após admin:init, execute php vendor/bin/fxartisan admin:mail --init. A operação cria somente a tabela da fila, não envia mensagens. Não habilite o site com mail configurado antes dessa inicialização.
  3. Execute php vendor/bin/fxartisan module:refresh para reconhecer a versão 0.1.1 do Admin e module:doctor. O callback reset_delivery anterior continua disponível; configure mail ou reset_delivery, nunca ambos.
  4. Consulte php vendor/bin/fxartisan admin:mail --status. Exibe apenas contagens pending, failed e expired.
  5. Processe com php vendor/bin/fxartisan admin:mail --limit=20. Sem --init ou --status, o comando envia mensagens reais. Configure seu agendador de deploy para executá-lo periodicamente, por exemplo a cada minuto. Nenhum agendamento é criado automaticamente pelo framework.

A requisição de recuperação somente grava a fila. O endereço e o link com token são cifrados com AES-256-GCM no SQLite; a chave fica fora do banco. O hash de destinatário permite substituir mensagens pendentes para a mesma conta. Esse hash não anonimiza o email contra tentativas de adivinhação. A tabela de tokens de autenticação continua guardando somente hashes; a fila precisa preservar o token cifrado até a entrega.

O trabalhador reserva cada mensagem por cinco minutos, libera o lock do banco antes de acessar a rede e tenta no máximo cinco vezes. Falhas recebem atrasos de 30, 60, 120 e 240 segundos antes das novas tentativas. Após a quinta tentativa, a mensagem fica em failed até expirar. Cada execução elimina mensagens expiradas. Mensagens têm janela máxima de 30 minutos na fila; o token pode vencer antes da entrega. Solicite novo link quando necessário.

Não há garantia de entrega exatamente uma vez: uma interrupção após o servidor aceitar a mensagem pode causar reenvio. Uma mensagem já em trânsito não pode ser cancelada ao pedir novo link; o token anterior será rejeitado pelo fluxo de recuperação. Reservas expiradas permitem recuperação após queda; um transporte customizado que durar mais que cinco minutos pode provocar duplicidade.

Não troque FX_MAIL_KEY com mensagens pendentes: uma chave incorreta impede decifrar e consome tentativas. Planeje drenagem da fila e rotação da chave no deploy. Mantenha banco e backups privados. Não registre a DSN, a chave ou o corpo das mensagens em logs. Erros de transporte retornam informação genérica para evitar exposição de credenciais.

Teste reproduzível: instale examples/smtp e execute php tests/integration/smtp.php na raiz. O capturador aceita uma conexão loopback e não faz relay. Isso verifica SMTP/MIME local, não autenticação, TLS remoto, reputação do domínio, autorização do remetente ou entrega na caixa postal. Consulte a documentação do Symfony Mailer para requisitos do transporte.

Operação, API e problemas comuns

Respostas privadas usam no-store. Formulários exigem X-CSRF-TOKEN; obtenha o token em GET /admin/api/session. Erros: 401 requer login, 403 acesso/CSRF negado, 409 conflito, 422 entrada inválida, 429 limite, 500 falha interna. A API limita corpos a 16 KiB. Faça backup do SQLite e do estado dos módulos antes de mudanças.

config/admin.php aceita logger(evento, contexto). O exemplo registra eventos em storage/admin.log; não grava senha ou token. Configure rotação, retenção e acesso aos logs. Sem logger, erros críticos usam error_log do PHP. Configure sessão PHP em diretório privado e gravável pelo usuário da aplicação.

Página 404: confira ativação fx-admin e bootstrap. Banco ausente: execute admin:init. Cookie não persiste em HTTP: Secure deve ser false somente no exemplo local. Conta bloqueada: aguarde a janela do limitador e confira estado ativo. Formulário expirado: recarregue para obter CSRF novo. Sessão de outro sistema já iniciada: este painel é standalone; WordPress deve usar sua autenticação nativa.

Dados de usuários são inseridos no DOM como texto. Links de ajuda estão disponíveis no cabeçalho e nas janelas. O pacote inclui HTML/CSS/JavaScript offline, sem CDN ou build. A API retorna listas pequenas; as telas carregam dados ao abrir as janelas.

Extensões de negócio (Admin 0.1.2)

Providers confiáveis podem registrar telas e APIs. Declare permissões extras em config/admin.php na chave permissions, lista de strings como contacts.view. AdminStore aceita essa lista no segundo argumento; permissionCatalog() retorna o catálogo completo.

$panel->addArea('contacts', 'Contatos', '/contacts', 'contacts.view');
$panel->api($router, 'GET', 'contacts', 'contacts.view',
    fn ($request, $data, $user) => $store->listing($request->query->all()));

addArea exige identificador único, caminho local absoluto simples e permissão configurada; abre a URL em iframe do FX Windows. session inclui areas filtradas por acesso. Registre em cada bootstrap, no provider de módulo ativo dependente de fx-admin. Sirva a tela e recursos pelo provider; os dados devem ficar em APIs protegidas. O manifesto sozinho não executa essa integração.

api registra /admin/api/{path}, com sessão, limite de corpo, CSRF e exigência conjunta de dashboard.view e da permissão informada. A ação recebe Request, array e usuário e retorna array JSON com HTTP 200. Use uma permissão para rotas privadas: null torna a rota pública, reservado a fluxos como login. Escolha nomes exclusivos sem substituir rotas internas. Lance FieldErrors(['email' => 'Informe um email válido.']) para retornar 422 com errors por campo.

Compatibilidade/migração: assinaturas antigas continuam válidas e mantêm o catálogo original sem configuração extra. O Administrador reservado passa a ter todas as permissões explicitamente configuradas, inclusive em bancos existentes; demais perfis exigem concessão. Remover uma permissão da configuração suspende seu efeito; restaurá-la pode reativar concessões armazenadas. Não há alteração de esquema. Após atualizar o pacote, execute module:refresh fx-admin para reconhecer 0.1.2. Corpos [] continuam aceitos como vazios por compatibilidade; listas não vazias são rejeitadas.

Resultado esperado: cartão adicional somente para usuários autorizados. Confira ativação, configuração, dependência fx-admin e perfil se não aparecer; atualize o painel. Desativar remove as rotas no próximo bootstrap sem apagar dados. O exemplo Contatos do repositório demonstra instalação, uso e validação. Não existe catálogo remoto de módulos de negócio nesta entrega.

Escopo desta entrega

Backend SQLite, um perfil por usuário, prefixo /admin fixo, sem MFA, sem OAuth, sem integração de email pronta e sem banco distribuído. Ainda não há benchmark, validação de alta concorrência, matriz de versões modernas ou revisão visual completa no navegador. Não considerar esta entrega uma certificação de segurança ou de escala.

As primitivas existentes de fx-auth permanecem compatíveis. O novo painel usa sua própria configuração de sessão e consulta fresca de identidade. Ele não deve substituir o painel nativo do WordPress. MySQL/PostgreSQL, adaptações de esquema e infraestrutura distribuída precisam de uma etapa específica.

Referências: configuração de sessões PHP e recuperação de senha OWASP. Links externos são complementares; esta ajuda funciona offline.

Configurações de email

Objetivo: configurar a recuperação de senha pelo painel e compartilhar os mesmos valores com o processo da fila. Requer fx-admin atualizado, symfony/mailer ^6.4, banco inicializado, SMTP com SSL/TLS implícito e endereço HTTPS do painel.

  1. Entre com o administrador principal (papel reservado 1) e abra Configurações de email.
  2. Informe servidor, porta (normalmente 465), usuário SMTP, senha, remetente autorizado pelo provedor e URL HTTPS terminada em /admin. Ative email e salve.
  3. Use Verificar conexão. Para testar entrega, informe o destinatário e clique em Enviar teste; confira também spam.
  4. Mantenha o trabalhador abaixo aberto em outro terminal, na raiz da aplicação. Encerre com Ctrl+C.
php vendor/bin/fxartisan admin:mail --watch --interval=10 --limit=20

O trabalhador consulta a fila automaticamente e relê a configuração a cada ciclo. Não é instalado como serviço do sistema. Em produção, use um supervisor para manter o comando ativo ou agende admin:mail --limit=20. Evite processos concorrentes desnecessários. --cycles=2 limita a execução a dois ciclos para diagnóstico; sem limite, executa continuamente.

Onde fica e como outro processo lê

Os dados ficam no .env da raiz da aplicação, fora de public (no exemplo: examples/contacts/.env). O painel preserva outras variáveis e uma senha vazia mantém a atual. A senha e a chave da fila não são devolvidas pela API. A escrita usa bloqueio, revisão do formulário e substituição do arquivo. Proteja também backups e permissões do arquivo no servidor.

FX_MAIL_ENABLED="0"
FX_MAIL_HOST="smtp.example.com"
FX_MAIL_PORT="465"
FX_MAIL_USERNAME="suporte@example.com"
FX_MAIL_PASSWORD=""
FX_MAIL_FROM="suporte@example.com"
FX_MAIL_FROM_NAME="Minha aplicação"
FX_ADMIN_URL="https://painel.example.com/admin"
FX_MAIL_KEY=""

Exemplo desativado: use o painel para preencher e ativar. A chave de 64 caracteres hexadecimais é gerada ao salvar; preserve-a nas migrações para manter mensagens já enfileiradas legíveis. Não copie senhas para o Git. O painel exige configuração completa ao salvar, inclusive para desativar uma configuração existente.

Em aplicações próprias, habilite 'mail_settings' => true em config/admin.php e use AdminConfig::panel($root). Sem essa opção, o contrato anterior permanece. FX_MAIL_ENABLED=1 ativa e =0 desativa explicitamente; sem a variável, a configuração mail anterior continua válida. Precedência: ambiente real do servidor, .env, configuração legada. Quando há variáveis SMTP no ambiente real, a edição no painel fica bloqueada para evitar salvar valores sem efeito.

$config = \Fx\Framework\Admin\AdminConfig::read($root);
$mail = $config['mail'] ?? null;

Esse é o mesmo leitor usado pelo painel e pelo trabalhador. Outro processo PHP também pode analisar .env com Symfony Dotenv. O arquivo não é exportado automaticamente para variáveis globais nem para programas externos; esses programas precisam carregar o arquivo explicitamente. O parser e a dependência pertencem ao Admin, não ao Core.

Problemas comuns

Sem o botão: confira o papel principal, a opção mail_settings e a atualização do vendor. Mensagem aceita pelo SMTP não garante chegada à caixa. Recuperação aguardando: confira admin:mail --status e o trabalhador. Link expirado: solicite novo e mantenha o trabalhador ativo. Certificado HTTPS local exige o servidor HTTPS de teste disponível. Erro de revisão: reabra a janela. Sintaxe inválida no .env: corrija localmente sem divulgar seu conteúdo. A interface suporta SSL/TLS implícito; STARTTLS na porta 587 ainda não é oferecido.

Compatibilidade: mail.local.json continua como origem legada; ao salvar, os valores efetivos e a chave são preservados no .env. As rotas GET/POST /admin/api/mail/settings, POST /admin/api/mail/check e POST /admin/api/mail/test exigem o administrador principal; as escritas exigem CSRF. O teste recebe recipient e usa a configuração salva. A candidata 1.1.0-rc.1 publicada anteriormente não inclui esta etapa.

Seleções com FxSelect2

Objetivo: usar pesquisa e seleção uniforme nos formulários, inclusive janelas e conteúdo AJAX. Requer os arquivos locais fxwindows.js e fxwindows.css; não exige jQuery, CDN ou Select2 externo.

Uso e resultado esperado

<link rel="stylesheet" href="/assets/fxwindows.css">
<script src="/assets/fxwindows.js" defer></script>
<label>Perfil
  <select name="role_id" required>
    <option value="">Selecione</option>
    <option value="2">Editor</option>
  </select>
</label>

Ao carregar a página, todos os selects recebem FxSelect2 automaticamente. Novos campos inseridos no documento também são iniciados. Cada iframe precisa carregar seus próprios assets. O select original mantém name, value, validação e participação em FormData. Escolher uma opção dispara change; o Admin continua enviando JSON.

Seleção múltipla é suportada com multiple: clicar alterna a opção e mantém a pesquisa aberta; Limpar remove todas. Em seleção simples, Limpar usa a opção vazia ou a primeira opção habilitada. Use valores únicos nas opções. Campos e grupos desabilitados são respeitados. Setas e Enter operam a pesquisa; Escape fecha. Opções alteradas no DOM e reset do formulário atualizam a apresentação.

Compatibilidade e migração

A inicialização agora é automática onde fxwindows.js estiver carregado. Chamadas antigas a startFxForms() e new FxSelect2(select).start() continuam válidas e não duplicam o seletor. Formulários removidos liberam observadores e eventos. Atualize JS e CSS juntos; cópias públicas antigas precisam ser republicadas. Instalações mínimas sem FX Windows não carregam esse recurso.

Depois de alterar select.value por código, dispare select.dispatchEvent(new Event('change', {bubbles:true})). Para valores múltiplos no JSON, use Array.from(select.options).filter(option => option.selected).map(option => option.value). Botões internos são type=button; manipuladores de submit devem usar event.submitter ou procurar explicitamente o botão de envio.

Conferência e problemas comuns

  1. No Admin, abra Usuários e Novo usuário ou Editar.
  2. Em Perfil, pesquise uma opção, selecione e salve uma conta de teste.
  3. Reabra a conta e confira o perfil. Abra e feche a janela para conferir que existe somente um seletor.

Se aparecer o campo antigo, confira os assets publicados e recarregue com Ctrl+F5. Sem JavaScript, o select nativo permanece disponível. A validação de permissões continua obrigatória no servidor.

XAMPP, subpastas e URLs públicas

A raiz do projeto também pode ser acessada: http://localhost/nome-do-projeto/ redireciona para public/ quando mod_rewrite está disponível. O redirecionamento é temporário (302), sem fixar domínio ou nome da pasta. Arquivos privados e listagem de diretórios continuam bloqueados. Sem mod_rewrite, acesse public/index.php/admin diretamente; a raiz permanece bloqueada.

O Admin detecta a base pública pela requisição. CSS, JavaScript, ajuda, AJAX, logout e links de módulos usam essa base. A raiz da aplicação administrativa redireciona para o painel usando index.php, permitindo iniciar mesmo sem URLs reescritas.

  1. No XAMPP, instale o projeto e configure o administrador normalmente.
  2. Acesse http://localhost/nome-do-projeto/public/.
  3. Se necessário, use diretamente http://localhost/nome-do-projeto/public/index.php/admin.

Não é obrigatório criar VirtualHost. Os novos projetos HTTP/Admin incluem public/.htaccess com DirectoryIndex, AcceptPathInfo e regras de reescrita condicionais. O .htaccess da raiz bloqueia acesso HTTP a arquivos privados; public possui autorização própria. São regras para Apache 2.4 e dependem de AllowOverride autorizado pela hospedagem. Nginx e servidores que ignoram .htaccess exigem configuração equivalente. Em produção, prefira expor somente public.

Base manual opcional

APP_URL="http://localhost/meu-projeto/public/index.php"

Deixe APP_URL vazio para detecção automática. Nos projetos Admin gerados, config/admin.php lê o valor de .env e prioriza o ambiente real. Em aplicações próprias, passe app_url na configuração Admin ou defina APP_URL no ambiente do processo. A opção define a base dos links; não cria regras de servidor. Use sem /admin no final. Apenas o caminho é usado pelo painel, mantendo links na mesma origem. Não são aceitas credenciais, query ou fragmento.

A recuperação continua exigindo FX_ADMIN_URL HTTPS fixo, agora também com subpasta, por exemplo https://exemplo.com/projeto/public/index.php/admin. APP_URL não substitui essa configuração nem instala certificado HTTPS.

Projetos existentes e módulos

Atualize fx-admin e copie os novos arquivos .htaccess do gerador quando ainda não houver regras próprias. Não sobrescreva regras personalizadas. O exemplo Contatos também adapta seus links e AJAX. Outros módulos devem gerar suas URLs com a base da requisição; o framework não reescreve arbitrariamente HTML ou JavaScript de terceiros.

Compatibilidade: caminhos /admin continuam disponíveis quando public é a raiz. Panel recebeu um último argumento opcional appUrl, preservando chamadas anteriores. A rota / do Admin agora redireciona para o painel; se a aplicação registrar sua própria rota / antes do módulo, ela tem precedência. Para atualizar assets antigos, recarregue com Ctrl+F5.

Conferência

Confira login, estilos, ajuda e chamadas JSON. Acessos a .env, config e vendor pela URL devem ser negados. Se .htaccess não for permitido, a hospedagem precisa fornecer proteção equivalente e suporte a PATH_INFO para index.php/admin. O suporte foi verificado no Apache/XAMPP local; não significa compatibilidade automática com qualquer servidor.
