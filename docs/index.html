Disponível · base atual

01 · Visão e estado atual

O FX reúne container Illuminate, Eloquent, HTTP, roteador, middleware, validação, autenticação por sessão, autorização, Smarty e ferramentas CLI. O pacote completo preserva esses recursos. O FX Core agora também pode ser instalado separadamente, sem a camada web.

Core, HTTP, Database, View, Console, Auth, Validation, Windows e WordPress já possuem pacotes locais independentes. Presets, download de módulos pelo Artisan e dashboard com gerenciamento de usuários ainda serão implementados.

A tag v1.0.01 preserva o código original. A constante interna do Artisan ainda informa 0.2.0. A etapa 2 corrige validação, Request e erros HTTP e adiciona proteção CSRF às novas aplicações web. Consulte a migração no histórico.

Use o índice por assunto, a busca local ou links como index.html#formularios. Este manual funciona offline; para imprimir todos os tópicos, use a função de impressão do navegador.

02 · Instalação passo a passo

Preparar o framework local

O pacote declara PHP 8.1 ou superior e Composer 2. A compatibilidade com versões mais recentes deve ser verificada pelos testes. Na pasta do framework:

composer install
php vendor/bin/phpunit --do-not-cache-result
php bin/fxartisan list

Resultado: dependências em vendor/ e lista de comandos disponível. composer.lock preserva as versões usadas pelo projeto.

Usar em outra aplicação

Crie uma pasta irmã, como minha-aplicacao, e coloque este conteúdo no composer.json dela:

{
  "name": "fx/minha-aplicacao",
  "repositories": [{"type": "path", "url": "../fxframework"}],
  "require": {"fxfavalessa/fx-framework": "@dev"},
  "autoload": {"psr-4": {"App\\": "app/"}}
}

Na pasta da aplicação, execute:

composer install
php vendor/bin/fxartisan app:init
composer dump-autoload
php fxartisan serve --host=127.0.0.1 --port=8000

Abra http://127.0.0.1:8000. A rota inicial deve mostrar “FX Framework”. O comando app:init cria diretórios e arquivos ausentes; ele não cria o banco nem instala um painel administrativo.

Execute geradores na raiz da aplicação consumidora. O diretório atual determina onde os comandos legados escrevem os arquivos.
Disponível · Etapa 3A

Instalação mínima com FX Core

Escolha fxfavalessa/fx-core para container, configuração e providers sem HTTP, banco, Smarty, Console ou painel. O pacote completo fxfavalessa/fx-framework já contém o Core; aplicações existentes podem continuar usando-o.

Experimentar neste repositório

composer install --working-dir=examples/minimal --no-dev
php examples/minimal/index.php
php examples/minimal/verify.php

Resultado esperado: “Ola, FX Core” e confirmação de instalação independente. O exemplo tem seu próprio vendor e não usa o autoload da raiz. O script verifica dependências, injeção, providers e preservação da sessão e do container hospedeiro.

Usar em sua aplicação

Em uma pasta irmã de fxframework, crie composer.json:

{
  "name": "fx/minimo",
  "repositories": [{"type": "path", "url": "../fxframework/packages/core"}],
  "require": {"fxfavalessa/fx-core": "@dev"}
}

Execute composer install e use:

require __DIR__ . '/vendor/autoload.php';
$app = new Fx\Framework\Foundation\CoreApplication(__DIR__);
$app->config()->set('app.name', 'Meu projeto');
echo $app->config()->get('app.name');

O Core não carrega .env, rotas, sessão ou arquivos de configuração automaticamente. As instâncias de configuração são isoladas. Use get, set e all; pontos em chaves representam níveis de arrays. CoreApplication não substitui o container global por padrão. Application web mantém o comportamento legado.

Instalação verificada: FX Core e quatro dependências de infraestrutura. Isso comprova separação de pacotes, não ganho de latência. O container Illuminate foi mantido para preservar compatibilidade. O Core não inclui Artisan. O pacote fx-wordpress oferece a integração nativa com WordPress.

Consulte o guia HTML distribuído com o Core, incluindo configuração, providers e migração. Instalação local em desenvolvimento; publicação dos pacotes e releases independentes ainda pendentes.

Resultado: aplicação HTTP sem Eloquent nem Smarty. Adicione o mapeamento PSR-4 App\ para app/ no manifesto se criar classes da aplicação. O wildcard de repositories precisa estar no projeto consumidor; Composer não herda repositórios das dependências.

Quais comandos aparecem?

CLI sozinho: about, make:controller, limpeza de cache e instalação de componentes/presets. Com HTTP: app:init, serve, route:list, make:request e make:middleware. Com Database: models e migrations (requer bootstrap da aplicação configurando a conexão). make:crud exige HTTP + Database + View. Com Windows: fxwindows:install. Com Modules: module:status/doctor/enable/disable/refresh.

Verificar um cenário local

composer install --working-dir=examples/view --no-dev
php examples/verify-package.php view

Troque view por http, database, console, auth, validation, windows, web ou modular. Cada exemplo usa vendor próprio. O teste modular combina todos os pacotes sem instalar fx-framework.

Pacotes de desenvolvimento local: ainda não houve publicação de releases. HTTP mantém Illuminate HTTP e Database mantém Eloquent; independência de instalação não significa que essas bibliotecas foram substituídas. Auth oferece primitivas, não painel pronto.
Etapa 6 · backend SQLite

Painel FX Windows: login, usuários e permissões

fx-admin é opcional e instala o painel com formulários AJAX/JSON, usuários paginados, perfis e permissões validadas no servidor. O núcleo mínimo continua independente. O pacote completo agora exige extensões PDO e pdo_sqlite, além dos requisitos anteriores.

cd examples/admin
composer install
php vendor/bin/fxartisan admin:init --email=seu-email@example.com
php vendor/bin/fxartisan module:enable fx-admin
php -S 127.0.0.1:8080 -t public public/index.php

Informe a senha no terminal e abra http://127.0.0.1:8080/admin. Sem senha padrão; admin:init não redefine contas existentes. O exemplo é HTTP local. Em HTTPS, configure secure_cookie=true e mantenha banco e logs fora de public.

Para outro projeto, preset:install admin --constraint=@dev adiciona os pacotes. Copie e adapte a configuração e o bootstrap do exemplo; o preset não gera esses arquivos automaticamente. Há ajuda contextual nas janelas, acesso por perfil e bloqueio da remoção do último administrador ativo.

Recuperação usa token com hash, expiração e uso único, mas depende de reset_delivery configurado para sua fila/provedor de email. O exemplo não envia mensagens. O painel é standalone; plugins WordPress devem continuar usando identidade nativa.

WordPress: plugin com integração nativa

O pacote fx-wordpress usa apenas Core. Não inicia sessão PHP, kernel HTTP ou banco paralelo. Hooks, usuário atual, capabilities, wpdb, opções e REST API pertencem ao WordPress hospedeiro.

composer install --working-dir=examples/wordpress --no-dev

Copie examples/wordpress com vendor para wp-content/plugins/fx-example em um site de desenvolvimento. Ative o plugin e abra Configurações → FX Example. Um administrador pode salvar o nome por AJAX/JSON; o formulário usa X-WP-Nonce e o servidor exige manage_options.

O adaptador oferece app(), action(), filter(), rest(), user(), can(), permission(), database(), option() e updateOption(). Escolha slugs únicos para separar rotas e opções. Callbacks REST recebem os objetos nativos do WordPress.

Manual do adaptador · Ajuda do plugin · Reproduzir a integração

Verificado em WordPress 6.4.3, PHP 8.1.12 e MariaDB 10.4.27 descartável: 28 verificações reais, incluindo dois adaptadores e hooks nativos, permissões, sanitização e nonces. UI no navegador, multisite, versões recentes e bibliotecas conflitantes ainda não foram validados. O teste não alterou os sites existentes.

04 · Container e providers

Use o container para resolver dependências. bind registra implementações e singleton compartilha uma instância. Providers agrupam configuração e inicialização.

use Fx\Framework\Foundation\Application;
use Fx\Framework\Support\ServiceProvider;

final class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->instance('app.nome', 'Minha aplicação');
    }
}

$app = new Application(dirname(__DIR__));
$app->registerProviders([AppServiceProvider::class])->boot();

Resultado: $app->make('app.nome') retorna o nome registrado. O bootstrap gerado ainda não registra seus providers nem chama boot(); acrescente isso ao integrá-los.

O Request atual é registrado antes da resolução de middleware e controllers, inclusive quando o dispatcher é usado diretamente. Os tipos Request do FX e do Illuminate e o alias request recebem a mesma instância. Não registre como singleton controllers ou serviços que armazenem a requisição: objetos já construídos não são recriados. Workers persistentes ainda não são um modo suportado.

05 · Rotas, middleware e respostas

Em routes/web.php, o bootstrap disponibiliza $app e o arquivo obtém $router. Uma rota pode apontar para closure ou [Controller::class, 'metodo'].

use Fx\Framework\Http\Request;
use Fx\Framework\Http\Response;

$router->get('/status', fn () => ['status' => 'ok']);
$router->get('/clientes/{id}', fn (string $id) => ['id' => $id]);
$router->post('/eco', function (Request $request) {
    return Response::json(['name' => $request->input('name')]);
});

Arrays viram JSON no Kernel; null vira 204; strings viram conteúdo de resposta. Use Response::json($dados, 201) para definir o status de criação.

Middleware implementa Fx\Framework\Middleware\Middleware, com process(Request $request, callable $next): mixed. Associe com ->middleware(MinhaClasse::class). Chame $next($request) para continuar.

resource('/clientes', Controller::class) registra GET da lista, POST, GET por id, PUT por id e DELETE por id. Não inclui telas create/edit nem PATCH. Rotas inexistentes retornam 404 e método incompatível retorna 405.

ModelNotFoundException agora retorna 404, sem revelar nome do model ou IDs em produção. Exceções que implementam HttpExceptionInterface preservam status e cabeçalhos, como Retry-After; erros 5xx ocultam detalhes em produção. HEAD automático, grupos e nomes de rotas utilizáveis ainda não fazem parte da API documentada.

06 · Validação, AJAX e JSON

Valide no servidor e persista apenas os dados retornados por validate(). A API atual aceita required, nullable, string, integer, numeric, boolean, array, email, min, max, in e confirmed.

$router->post('/validar-contato', function (\Fx\Framework\Http\Request $request) {
    $data = $request->validate([
        'name' => 'required|string|max:255',
        'email' => 'required|email',
    ]);
    return ['data' => $data];
});

Este endpoint apenas valida e devolve dados; não grava nada. Nas novas aplicações web ele também exige CSRF. Renderize -{csrf_field}- no formulário e passe o valor do campo _csrf como terceiro argumento da função abaixo:

async function validarContato(name, email, csrfToken) {
  const response = await fetch('/validar-contato', {
    method: 'POST',
    headers: {'Accept': 'application/json', 'Content-Type': 'application/json', 'X-CSRF-TOKEN': csrfToken},
    body: JSON.stringify({name, email})
  });
  const payload = await response.json();
  if (response.status === 422) return {errors: payload.errors};
  if (!response.ok) throw new Error(payload.message || 'Falha na requisição');
  return payload;
}

Trate também rejeição da Promise em falhas de rede. Exiba mensagens com textContent e associe erros aos campos. Para formulários que modificam dados com sessão autenticada, integre a verificação CSRF descrita a seguir.

Regras corrigidas: required rejeita ausência, null, texto vazio ou só espaços e array vazio; aceita zero e false. Campos ausentes sem required são opcionais. nullable mantém a compatibilidade com null e string vazia, mas não anula required. min/max medem caracteres de strings e itens de arrays; use numeric ou integer para comparar o valor numérico de texto. integer não aceita booleanos. A validação não implementa todas as regras do Laravel.

07 · Login, permissões e CSRF

SessionGuard oferece attempt, login, logout, user, check e guest. A aplicação implementa UserProvider com retrieveById, retrieveByCredentials e validateCredentials; o usuário implementa Authenticatable::getAuthIdentifier().

No provider real, consulte o usuário e use hash de senha adequado com password_verify(); não armazene senha em texto puro. Registre o guard no container antes de usar o middleware Authenticate.

$guard = new \Fx\Framework\Auth\SessionGuard($provider);
$app->instance(\Fx\Framework\Auth\SessionGuard::class, $guard);
$gate = new \Fx\Framework\Auth\Gate($guard);
$gate->define('clientes.visualizar', fn ($user) => $user->role === 'admin');
$gate->authorize('clientes.visualizar');

Exemplo de integração: $provider é sua implementação e role é um atributo do seu usuário. A autorização negada resulta em 403. Verifique permissões no endpoint, mesmo se o botão estiver oculto.

Proteção de formulários com sessão

Csrf::token() gera o token; envie-o no formulário ou JSON e verifique Csrf::validate($token) antes de gravar dados. O token deve ser uma string; rejeite entradas inesperadas.

use Fx\Framework\Http\Csrf;
use Fx\Framework\Http\Response;

$token = $request->input('_csrf');
if (!is_string($token) || !Csrf::validate($token)) {
    return Response::json(['message' => 'Token CSRF inválido.'], 403);
}
Novas aplicações geradas por app:init registram VerifyCsrfToken no router web; formulários de make:crud incluem -{csrf_field}-. POST, PUT, PATCH e DELETE exigem token no corpo _csrf (formulário/JSON) ou cabeçalho X-CSRF-TOKEN. O cabeçalho tem precedência. O helper csrf_field não armazena o token no cache Smarty e acompanha a sessão atual. Tokens na URL não são aceitos. GET, HEAD e OPTIONS não iniciam sessão por esse middleware. Telas de login, recuperação configurável e gerenciamento de usuários/perfis agora estão no pacote fx-admin; consulte a seção Admin.

08 · Banco, migrations e CRUD

Database::boot($connection) inicializa Eloquent; o bootstrap gerado já chama esse método. Crie primeiro o banco e configure credenciais. Depois execute na aplicação:

php fxartisan make:crud Cliente
composer dump-autoload
php fxartisan migrate:status
php fxartisan migrate
php fxartisan route:list

Resultado: model, request, controller, templates simples com campo CSRF, migration e cinco rotas para /clientes. O controller gera JSON e pagina a lista; as views ainda não são conectadas às ações. O model gerado usa $guarded = []; mantenha o uso de dados validados e considere uma lista explícita de campos permitidos.

make:migration create_produtos_table cria uma migration inicial com id, name e timestamps. Ajuste seu schema antes de executá-la. migrate:rollback reverte o último lote.

migrate:fresh apaga todas as tabelas da conexão configurada. Use em banco descartável. Migrations não são globalmente atômicas; uma falha pode deixar alterações parciais. Revise o estado antes de repetir.

Dica: revise os nomes de tabela gerados, especialmente palavras com plural irregular. O gerador concatena “s”; Eloquent pode adotar outra convenção.

09 · Views e FX Windows

Crie os diretórios de templates, compilação e cache e instancie a view:

$view = new \Fx\Framework\View\View(
    $app->basePath('resources/views'),
    $app->basePath('storage/tmp'),
    $app->basePath('storage/cache')
);
echo $view->render('inicio.tpl', ['nome' => 'Maria']);

Em inicio.tpl, use -{$nome|escape:'html'}-. O wrapper não habilita escape automático global. Escape dados conforme o contexto HTML, atributo ou JavaScript. Cada render limpa as variáveis atribuídas.

Publicar as janelas

php fxartisan fxwindows:install

O comando publica JavaScript e CSS em assets da aplicação. Em um template Smarty:

-{fxwindows_assets forms=true}-
-{fxwindow id="clientes" texto="Novo cliente" url="/clientes/novo"
  titulo="Cadastro de clientes" largura=900 altura=600 nivel=1 foco="#nome"}-

Crie a rota /clientes/novo e o formulário correspondente; o resource atual não a cria. O helper aceita tipo button ou link, classe, título, dimensões, nível e seletor de foco. forms=true inicializa os comportamentos de formulário; consulte a implementação antes de substituir atalhos da aplicação.

Carregue assets uma vez no layout. O dashboard completo ainda será construído; FX Windows disponível hoje é a biblioteca de janelas e formulários.

11 · Módulos, presets e WordPress

module:list, module:install e preset:install coordenam a instalação de componentes pelo Composer. O pacote opcional fx-modules agora fornece registro e ciclo de ativação dos módulos de negócio. O painel inicial SQLite está disponível em fx-admin.

Instalar conforme a necessidade

Requisitos: PHP ^8.1, Composer 2 e um projeto com composer.json. Execute os comandos na raiz desse projeto. O catálogo é fechado aos onze componentes FX disponíveis; não aceita URLs ou pacotes de terceiros.

php vendor/bin/fxartisan module:list
php vendor/bin/fxartisan module:install view --constraint=@dev --dry-run
php vendor/bin/fxartisan module:install view --constraint=@dev
php vendor/bin/fxartisan preset:install api --constraint=@dev --dry-run
php vendor/bin/fxartisan preset:install api --constraint=@dev

Em uma aplicação sem Console instalado, você também pode chamar o executável da cópia local do framework: php ../fxframework/bin/fxartisan preset:install minimal --constraint=@dev. O diretório atual determina o destino. O preset minimal não adiciona o Console ao projeto.

PresetRequisitos adicionadosUso
minimalfx-coreContainer, configuração e providers.
apifx-http e fx-consoleBase para respostas JSON, rotas e CLI; sem autenticação pronta.
wordpressfx-wordpressAdaptador e Core; WordPress deve existir no ambiente.
adminfx-admin e fx-consolePainel SQLite; configurar e executar admin:init.

O Composer resolve as dependências transitivas. Presets adicionam requisitos, sem remover pacotes não selecionados. Aplicar minimal em um projeto completo não o transforma em uma instalação enxuta. A restrição informada substitui a dos pacotes selecionados; revise o diff do manifesto e do lock.

Resultado: composer.json, composer.lock e vendor atualizados pelo Composer. Abra uma nova execução do Artisan para carregar os comandos recém-instalados. Esses comandos instalam pacotes; não criam o esqueleto de uma aplicação nem registram providers. No preset API, configure bootstrap e rotas conforme a ajuda HTTP. app:init gera uma base web com CSRF e não é um gerador específico de API.

Versões e simulação

Os pacotes FX ainda não foram publicados. Para os exemplos locais, configure repositories do tipo path apontando para ../fxframework/packages/*, minimum-stability: dev e prefer-stable: true no manifesto consumidor. Use --constraint=@dev. A restrição padrão ^1.0 é destinada a futuras releases; não significa que elas já estejam disponíveis.

--dry-run pede ao Composer uma simulação: não modifica o manifesto/lock nem instala vendor. Pode acessar os repositórios e o cache do Composer. A saída do Composer pode dizer “composer.json has been updated” durante a simulação; os arquivos permanecem preservados ao final.

Problemas comuns e próximos passos

  • Composer não encontrado: informe --composer=C:/composer/composer.phar, ajustando o caminho. Use aspas se houver espaços. No Unix, um executável Composer também é aceito. Wrappers .bat/.cmd não são aceitos; use o PHAR correspondente.
  • Pacote não encontrado: confira o repositório path no consumidor e a restrição @dev. Repositórios declarados apenas na dependência não são herdados.
  • Versões incompatíveis: consulte a saída do Composer e revise requisitos, lock e vendor. O comando retorna erro; não ignora requisitos de plataforma nem força atualização geral. Falhas de resolução normalmente restauram manifesto e lock; interrupções e falhas durante instalação não têm garantia de rollback completo.
  • Ambiente com COMPOSER ou COMPOSER_VENDOR_DIR: remova essas variáveis antes de usar os comandos, pois podem redirecionar os arquivos do projeto.
  • Scripts e plugins Composer ficam desabilitados nesta operação. Se seu projeto depende deles, execute os passos de configuração necessários separadamente, após revisão. Migrations e publicação de assets também são explícitas: instalar windows não executa fxwindows:install.
  • O preset admin adiciona fx-admin e fx-console. A configuração e a criação da primeira conta são explícitas; veja a seção Admin. O ciclo de módulos usa fx-modules.

Referência: comando require do Composer. Este manual funciona offline; o link externo é apenas complementar.

Ciclo de módulos — etapa 5B

Instale fx-modules, registre os manifestos em config/modules.json e use module:enable ID, module:disable ID, module:status e module:doctor. A ativação inclui dependências registradas; a desativação preserva dados e é bloqueada por dependentes ativos.

php vendor/bin/fxartisan module:install modules --constraint=@dev
php vendor/bin/fxartisan module:enable contacts
php vendor/bin/fxartisan module:doctor

O exemplo pressupõe um módulo contacts registrado e com provider no autoload. No bootstrap, chame ModuleManager::register($app) antes de boot(). O estado fica em storage/framework/modules.json. Depois de atualizar código pelo Composer e revisar migrations/configuração, module:refresh reconhece as versões novas; ele não baixa pacotes.

Veja o manual completo de módulos para o contrato JSON, passos de integração, atualização e solução de erros. O exemplo Hello permite testar sem HTTP ou banco. Rotas, assets e permissões do manifesto são metadados, sem execução ou concessão automática.

No WordPress, o adaptador utiliza hooks, usuários, capabilities, wpdb e REST nativos. Veja o guia WordPress. Detalhes: arquitetura alvo.

Metas e práticas

12 · Velocidade e crescimento

Priorize respostas pequenas, paginação no servidor, índices adequados, seleção de campos e carregamento de assets quando necessário. AJAX reduz recargas; não elimina consultas lentas nem torna a aplicação automaticamente escalável.

Vamos medir endpoint JSON simples, consulta paginada e operação autenticada: latência p50/p95, memória, consultas, bytes transferidos e tamanho instalado. Comparações usarão o mesmo ambiente, dados e carga.

Cache, filas e armazenamento externo serão integrações opcionais. Workers persistentes só serão considerados suportados após testes de isolamento do estado de requisição.

Ainda não há benchmark que demonstre vantagem de desempenho sobre Laravel. A meta de leveza será verificada antes de divulgar números.
Diagnóstico

13 · Solução de problemas

Autoload não encontrado ou classe App inexistente

Execute composer install, confira o mapeamento PSR-4 App no composer.json da aplicação e rode composer dump-autoload.

O .env não muda a conexão

O bootstrap lê variáveis do processo. Configure-as no servidor/shell ou integre um carregador explicitamente. Confira config/database.php e a extensão PDO do driver usado.

Resposta de validação veio em HTML

Envie Accept: application/json. O handler usa expectsJson para escolher o formato.

Erro ao iniciar sessão

Evite saída antes de iniciar autenticação/CSRF. Verifique BOM, espaços antes de <?php, debug impresso e configuração do diretório de sessões.

Template não compila ou aparece sem estilos

Confira permissões de storage/tmp e storage/cache, delimitadores Smarty e publicação dos assets. O endereço público deve corresponder ao caminho usado pelo helper.

Erro 500 sem detalhes

Em ambiente local, ative APP_DEBUG e consulte o log do PHP. O handler atual não grava exceções em storage/logs automaticamente. Modelos ausentes retornam 404 desde a etapa 2.

15 · Versões e manutenção da ajuda

v1.0.01 · Estado original

Marco Git local preservado antes das alterações. Dependências podem ser restauradas com Composer. Não mova a tag histórica.

Etapa 1 · 7 de setembro de 2026

Central de ajuda offline, busca local, índice por assunto, plano modular e regras de manutenção. Sem mudança no comportamento PHP.

Etapa 2 · Correções e migração

Validação, registro da requisição, 404 de modelos e status HTTP corrigidos. Middleware CSRF e helper Smarty adicionados, sem novas dependências Composer.

Aplicações existentes: app:init preserva arquivos já criados. Para proteger o router web, acrescente o registro abaixo em routes/web.php, depois de obter $router. Insira -{csrf_field}- dentro dos formulários existentes e envie _csrf ou X-CSRF-TOKEN em cada operação de escrita.

$router->middleware(\Fx\Framework\Middleware\VerifyCsrfToken::class);

Esse registro protege todas as rotas do router. Se misturar APIs sem sessão e páginas web, aplique ->middleware(VerifyCsrfToken::class) somente às rotas web apropriadas. Routers criados diretamente continuam sem CSRF obrigatório; não desative a proteção de endpoints autenticados por cookie para contornar erros.

Revise regras que dependiam do comportamento anterior: acrescente required quando ausência deve ser erro e numeric/integer quando min/max deve comparar valor. Atualize clientes que tratavam registro inexistente como 500 para tratar 404. Os formulários e arquivos de rotas existentes não são sobrescritos pelo gerador.

Etapa 3A · Core independente

Container e ServiceProvider foram movidos para packages/core, com namespaces preservados. Application completa estende CoreApplication e mantém a inicialização web. Atualize o autoload com composer dump-autoload após atualizar o checkout. Evite require de caminhos internos antigos.

ServiceProvider recebe CoreApplication. Providers com uma redeclaração da propriedade protegida $app tipada como Application precisam remover a redeclaração ou adotar CoreApplication. Providers que dependem de serviços web continuam próprios do pacote completo.

Etapa 3B · Componentes opcionais

As classes antes em src/ estão nos pacotes; assets estão em packages/windows/resources/fxwindows. Namespaces, bin/fxartisan da raiz e o pacote completo permanecem. Execute composer install para regenerar o autoload e use Windows\Assets::directory() para localizar assets sem caminhos fixos. O CLI limita comandos aos componentes instalados. Aplicações já geradas preservam seus arquivos; para remover banco de uma aplicação antiga, revise manualmente a chamada Database::boot no bootstrap.

Etapa 4 · WordPress

Adaptador e plugin de exemplo disponíveis. Instâncias isoladas sobre o Core, recursos nativos do host e integração real documentada. Consulte o tópico WordPress para requisitos e limites.
