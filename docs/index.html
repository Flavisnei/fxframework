Admin e Contatos com MariaDB

Verificação: 117 testes e 643 assertions na suíte local com backend MariaDB; 34 verificações HTTP/CLI. As dez tarefas da CI da revisão 5bbb8c2 passaram, incluindo MariaDB 10.4 e 10.11.

Disponível nesta etapa: snapshots da revisão 5bbb8c2 publicados no repositório Composer. Admin 0.1.3 e Contatos 0.1.1 aceitam PDO mysql com tabelas InnoDB. Login, usuários, perfis, limites de tentativa, tokens e fila cifrada usam o banco configurado. SQLite continua sendo o padrão e conserva seu schema. Nenhuma dependência foi adicionada ao Core.

Configuração e requisitos

Requer PHP com pdo_mysql e banco MariaDB previamente criado em utf8mb4. O teste local utiliza MariaDB 10.4.27; outras versões precisam ser homologadas. Em config/admin.php, substitua apenas database pela configuração abaixo, preservando secure_cookie, permissões e demais opções:

'database' => [
 'driver' => 'mysql',
 'host' => '127.0.0.1',
 'port' => 3306,
 'name' => 'seu_banco',
 'username' => getenv('FX_DB_USER') ?: 'root',
 'password' => getenv('FX_DB_PASSWORD') ?: '',
],

Root com senha vazia serve somente ao ambiente local autorizado. Para implantação, utilize uma conta própria com os acessos necessários. Não coloque credenciais no Git. AdminConfig::connection(config, create=false) é uma API nova e opcional; database como caminho SQLite absoluto permanece válido.

Para Contatos, crie config/contacts.php retornando ['database' => ...] com a mesma configuração ou outro banco MariaDB. Sem esse arquivo, Contatos mantém storage/contacts.sqlite. Use ContactStore::configured(root, create=false) para a conexão configurada.

Instalar e atualizar

Atualize o vendor do consumidor e execute admin:init para uma base nova; contacts:init cria a tabela sem apagar registros. Execute admin:mail --init se utilizar a fila. Ative os módulos e reconheça as versões com module:refresh após revisar a atualização. Reinicie processos longos. A inicialização HTTP não cria schema.

Migração: mudar a configuração não copia dados de SQLite para MariaDB. Esta etapa atende bases MariaDB novas e preserva bases SQLite existentes. Para migrar dados reais, mantenha backup e planeje transferência validada de IDs, perfis, hashes de senha e referências; não há importador automático nesta versão. Retorno exige restaurar configuração e vendor compatíveis com o banco de origem.

Transações e comportamento

DDL MariaDB executa commit implícito; a criação de tabelas ocorre antes da transação da primeira conta. Uma falha pode deixar tabelas vazias, e a inicialização pode ser repetida. Uma conta existente nunca é substituída. Operações críticas do Admin usam uma linha de bloqueio InnoDB por banco; isso preserva o último administrador, consumo único de token e contador de tentativas. A fila possui bloqueio próprio, liberado antes do transporte SMTP. Esses bloqueios podem limitar vazão sob alta concorrência.

Contatos mantém atualização/exclusão por versão e erro 409 em dados obsoletos. Tabelas novas usam utf8mb4_bin para unicidade sensível a maiúsculas; emails são normalizados pela aplicação. A busca LIKE pode ter diferenças de acentos/maiúsculas em relação ao SQLite. Nenhuma alteração de senha ou envio de email real é feita pela homologação.

Teste de carga no Apache com MariaDB local

Objetivo: exercitar FX HTTP e Database com leituras paginadas e gravações transacionais concorrentes. Não valida sessões, permissões ou tabelas do Admin. Requer Apache local na porta 80, PHP com PDO MySQL, Python 3 e vendor completo da raiz. O teste cria um banco aleatório fx_load_* e um endpoint temporário no webroot informado; os bancos e sites existentes são preservados.

python benchmarks/mariadb-http-load.py --webroot=C:/xampp/htdocs --port=3306 --clients=4 --requests=50

As credenciais padrão de teste são root e senha vazia, conforme o ambiente local autorizado. Para outro usuário, configure FX_TEST_MYSQL_USER e FX_TEST_MYSQL_PASSWORD no ambiente, sem gravar segredos na linha de comando. É necessário poder criar/remover bancos. Não use credenciais de produção.

Resultado esperado: JSON com latências separadas de leitura/gravação, quantidade de erros, linhas gravadas e contador. Cada cliente alterna GET e POST; cada POST insere um marcador único e incrementa o mesmo contador em uma transação. O total gravado e o contador devem coincidir com as gravações esperadas. Endpoint aceita somente loopback e token aleatório; acesso sem token precisa retornar 403. A configuração fica fora do webroot, e banco/pastas temporários são removidos ao terminar normalmente.

Resultado local: MariaDB 10.4.27, PHP 8.1.12 no Apache. Quatro clientes completaram 100 leituras e 100 gravações, sem erro e com integridade confirmada. Isso substitui a limitação do servidor PHP embutido para esta carga específica, mas não certifica capacidade de produção nem isolamento de várias máquinas. O JSON da rodada de oito clientes está em evidência de carga MariaDB. Essa rodada de oito clientes coincidiu com execução do PHPUnit; use-a para conferir integridade sob carga, não para comparar desempenho isolado.

Item 4 ainda pendente: AdminStore rejeita o driver mysql e ContactStore executa PRAGMA do SQLite. O teste reproduziu ambos os impedimentos. Portar o painel requer schema MariaDB, transações e bloqueios, limitador de login, recuperação e configuração compatíveis, além de testes HTTP de autorização. Não aponte a configuração atual do Admin para MariaDB.

Problemas comuns: 404 indica webroot/porta diferente do Apache ativo; falha de conexão exige conferir a porta do MariaDB; recusa de criação exige permissões no servidor de testes. Se houver encerramento forçado, confira somente os diretórios fx-load-* e banco fx_load_* criados por aquela execução antes de limpar. Latências dependem de CPU, disco, antivírus e demais tarefas; compare rodadas somente em ambientes equivalentes. Os itens de navegador e SMTP permanecem adiados pelo usuário.

Catálogos de instalação locais e remotos

Objetivo: escolher componentes e presets de um catálogo JSON da sua organização, além do catálogo embutido do FX Artisan. Requer FX Console atualizado, Composer 2 e um projeto com composer.json. Leitura HTTPS requer OpenSSL, allow_url_fopen habilitado e certificados confiáveis no PHP CLI.

Compatibilidade

Sem opções novas, module:list, module:install e preset:install mantêm o catálogo e comportamento anteriores. --catalog seleciona outro catálogo apenas para a execução atual; ele substitui a seleção embutida, sem mesclar nem persistir configuração. A API ComposerInstaller::install aceita um último argumento opcional InstallCatalog; chamadas existentes continuam válidas.

Passos e exemplo

Na raiz do checkout, liste o catálogo distribuído:

php bin/fxartisan module:list --catalog=docs/catalog.json

Para conferir o mesmo catálogo por HTTPS:

php bin/fxartisan module:list --catalog=https://raw.githubusercontent.com/Flavisnei/fxframework/097b04de98f46eef027199194515fcd2d933be4a/docs/catalog.json --catalog-sha256=3b1bc06b5dc11bc92b1f5811a8fac0254f6fc6cb7e34b405c480de3cf27ae7c3

O SHA-256 confere os bytes recebidos; obtenha o valor de uma revisão confiável. A URL do exemplo já está fixada na revisão testada; mantenha uma revisão explícita para reprodução duradoura. HTTPS exige hash explícito; o hash não substitui avaliação do fornecedor ou do código dos pacotes.

Na aplicação consumidora, use o mesmo catálogo e hash para simular a instalação. Exemplo com catálogo local previamente revisado e pacotes FX configurados por repositório Composer path:

vendor/bin/fxartisan preset:install minimal --catalog=catalogo.json --constraint=@dev --dry-run
vendor/bin/fxartisan preset:install minimal --catalog=catalogo.json --constraint=@dev

Resultado esperado: Composer resolve o pacote selecionado e suas dependências; a segunda execução instala. Scripts e plugins ficam desabilitados. Providers, permissões, migrations e ativação permanecem explícitos. Catálogo não adiciona repositórios ao composer.json e não hospeda pacotes: configure fontes confiáveis no consumidor. Os pacotes FX continuam disponíveis no checkout por path, sem publicação no Packagist.

Verificado: catálogo HTTPS lido com SHA-256 e preset mínimo instalado em consumidor temporário, com Core isolado. A CI do commit 097b04d passou nas oito tarefas, incluindo o teste de catálogo com Composer real.

Formato para catálogos próprios

{
  "schema": 1,
  "components": {
    "crm": {"package": "suaempresa/crm", "description": "Cadastro comercial"}
  },
  "presets": {"comercial": ["crm"]}
}

O exemplo suaempresa/crm é ilustrativo. Use nomes reais publicados no repositório Composer da sua organização. Aliases usam letras minúsculas, números e hífen; nomes de pacotes usam fornecedor/pacote. Presets referenciam aliases existentes, sem repetições. Somente os campos exibidos são aceitos; não inclua comandos, repositórios, credenciais ou código PHP.

Problemas comuns e dicas

Hash divergente: nenhum pacote é solicitado ao Composer; revise a mudança antes de atualizar o hash. Falha HTTPS: confira certificados e rede, sem desabilitar TLS. HTTP simples e redirecionamentos são recusados. Pacote não encontrado: configure o repositório Composer; o catálogo não publica nem baixa arquivos por conta própria. Limites: até 256 KiB, 200 componentes, 50 presets e tempo de leitura de 15 segundos. Guarde uma cópia local revisada para consultar o catálogo offline; instalar dependências pode exigir rede ou cache do Composer.

Verificação reproduzível: após instalar o vendor de examples/console, execute php tests/integration/catalog.php C:/composer/composer.phar na raiz (ajuste o caminho ao seu ambiente). O teste cria um pacote sintético e consumidor temporários, confere simulação, instalação real, autoload isolado e rejeição de adulteração, sem tocar nos seus projetos. Publicação de pacotes independentes e teste de capacidade HTTP permanecem etapas separadas.

Preparar o teste manual

Use uma cópia de desenvolvimento com banco vazio e dados fictícios. Siga a instalação de Contatos, incluindo criação do administrador, inicialização da tabela e ativação do módulo. Requer PHP, Composer, PDO SQLite e navegador com JavaScript. Na pasta examples/contacts, inicie:

Roteiro e resultados esperados

  1. Login: tente uma senha incorreta, confira a mensagem e entre com a conta de teste. Use Tab e Enter, verificando foco visível e campos acessíveis.
  2. Janelas: abra Usuários, Perfis, Módulos e Contatos. Confira fechamento, reabertura, conteúdo legível e controles acessíveis ao reduzir a janela do navegador.
  3. Usuários e permissões: crie um perfil de teste com acesso ao painel e somente leitura de Contatos, associe uma conta fictícia e entre com ela em outra sessão. A consulta deve funcionar e as ações de alteração devem estar indisponíveis; a autorização no servidor continua obrigatória.
  4. Contatos: com o administrador de teste, crie, busque e edite um contato fictício. Confira erros em campos inválidos e email duplicado. Abra a edição do mesmo registro em duas abas, salve uma e tente salvar a outra: deve aparecer conflito, sem sobrescrever silenciosamente a primeira alteração. Preserve o texto antes de recarregar.
  5. Ajuda e saída: abra a ajuda, busque termos com e sem acentos e teste os links do índice. Saia da conta e confirme que operações protegidas exigem autenticação novamente.

Problemas comuns: painel sem áreas pode indicar permissões ausentes; Contatos ausente pode indicar módulo não ativado. JavaScript antigo após atualização exige atualizar os assets do vendor do exemplo e recarregar. Se houver erro, anote passos, navegador, revisão e mensagem, sem registrar senhas ou dados pessoais.

Dica: registre cada cenário como aprovado, reprovado ou não executado. SMTP externo, recuperação com email real, carga HTTP e outros bancos precisam de validações próprias. CI aprovada não demonstra capacidade para grande porte.

05 · Rotas, middleware e respostas

Em routes/web.php, o bootstrap disponibiliza $app e o arquivo obtém $router. Uma rota pode apontar para closure ou [Controller::class, 'metodo'].

use Fx\Framework\Http\Request;
use Fx\Framework\Http\Response;

$router->get('/status', fn () => ['status' => 'ok']);
$router->get('/clientes/{id}', fn (string $id) => ['id' => $id]);

    return Response::json(['name' => $request->input('name')]);
});

Arrays viram JSON no Kernel; null vira 204; strings viram conteúdo de resposta. Use Response::json($dados, 201) para definir o status de criação.

06 · Validação, AJAX e JSON

Valide no servidor e persista apenas os dados retornados por validate(). A API atual aceita required, nullable, string, integer, numeric, boolean, array, email, min, max, in e confirmed.

$router->post('/validar-contato', function (\Fx\Framework\Http\Request $request) {
    $data = $request->validate([
        'name' => 'required|string|max:255',
        'email' => 'required|email',
    ]);
    return ['data' => $data];
});

Este endpoint apenas valida e devolve dados; não grava nada. Nas novas aplicações web ele também exige CSRF. Renderize -{csrf_field}- no formulário e passe o valor do campo _csrf como terceiro argumento da função abaixo:

async function validarContato(name, email, csrfToken) {
  const response = await fetch('/validar-contato', {
    method: 'POST',
    headers: {'Accept': 'application/json', 'Content-Type': 'application/json', 'X-CSRF-TOKEN': csrfToken},
    body: JSON.stringify({name, email})
  });
  const payload = await response.json();
  if (response.status === 422) return {errors: payload.errors};
  if (!response.ok) throw new Error(payload.message || 'Falha na requisição');
  return payload;
}

Trate também rejeição da Promise em falhas de rede. Exiba mensagens com textContent e associe erros aos campos. Para formulários que modificam dados com sessão autenticada, integre a verificação CSRF descrita a seguir.

Regras corrigidas: required rejeita ausência, null, texto vazio ou só espaços e array vazio; aceita zero e false. Campos ausentes sem required são opcionais. nullable mantém a compatibilidade com null e string vazia, mas não anula required. min/max medem caracteres de strings e itens de arrays; use numeric ou integer para comparar o valor numérico de texto. integer não aceita booleanos. A validação não implementa todas as regras do Laravel.

07 · Login, permissões e CSRF

SessionGuard oferece attempt, login, logout, user, check e guest. A aplicação implementa UserProvider com retrieveById, retrieveByCredentials e validateCredentials; o usuário implementa Authenticatable::getAuthIdentifier().

No provider real, consulte o usuário e use hash de senha adequado com password_verify(); não armazene senha em texto puro. Registre o guard no container antes de usar o middleware Authenticate.

$guard = new \Fx\Framework\Auth\SessionGuard($provider);
$app->instance(\Fx\Framework\Auth\SessionGuard::class, $guard);
$gate = new \Fx\Framework\Auth\Gate($guard);
$gate->define('clientes.visualizar', fn ($user) => $user->role === 'admin');
$gate->authorize('clientes.visualizar');

Exemplo de integração: $provider é sua implementação e role é um atributo do seu usuário. A autorização negada resulta em 403. Verifique permissões no endpoint, mesmo se o botão estiver oculto.

Proteção de formulários com sessão

Csrf::token() gera o token; envie-o no formulário ou JSON e verifique Csrf::validate($token) antes de gravar dados. O token deve ser uma string; rejeite entradas inesperadas.

use Fx\Framework\Http\Csrf;
use Fx\Framework\Http\Response;

$token = $request->input('_csrf');
if (!is_string($token) || !Csrf::validate($token)) {
    return Response::json(['message' => 'Token CSRF inválido.'], 403);
}
Novas aplicações geradas por app:init registram VerifyCsrfToken no router web; formulários de make:crud incluem -{csrf_field}-. POST, PUT, PATCH e DELETE exigem token no corpo _csrf (formulário/JSON) ou cabeçalho X-CSRF-TOKEN. O cabeçalho tem precedência. O helper csrf_field não armazena o token no cache Smarty e acompanha a sessão atual. Tokens na URL não são aceitos. GET, HEAD e OPTIONS não iniciam sessão por esse middleware. Telas de login, recuperação configurável e gerenciamento de usuários/perfis agora estão no pacote fx-admin; consulte a seção Admin.

Peso e isolamento

O Core com Illuminate 10 mantém quatro dependências externas. Illuminate 13 eleva esse total para onze, acrescentando reflection, collections, conditionable, macroable e polyfills exigidos por seu container; HTTP moderno também traz clientes PSR/Guzzle transitivos. Isso é custo real da atualização, não ganho automático de velocidade. O verificador mínimo permite somente as dependências conhecidas da linha selecionada e continua rejeitando HTTP, banco, templates e alteração da sessão do hospedeiro.

Resultado esperado: instalação independente, testes do consumidor aprovados e versões selecionadas visíveis em composer show. Banco não é migrado automaticamente e module:refresh não atualiza bibliotecas. A atualização deve ser revertida com o lock anterior e uma instalação consistente dos pacotes, conforme o guia de homologação.

Problemas comuns

PHP incompatível: atualize o runtime real ou mantenha a linha antiga temporariamente. Exemplo usa código velho: atualize seu próprio vendor por path. Sem --multisite, testa uma instalação simples. Com --multisite, executa primeiro a instalação simples e depois a conversão da rede. Testa também separação das opções, troca de papéis e restauração do site original. --host-autoload CAMINHO permite carregar primeiro o container de outro plugin. A compatibilidade vale para as combinações efetivamente registradas nas evidências, não para qualquer plugin. Namespaces PHP são globais: versões incompatíveis de uma mesma classe exigem resolução comum ou distribuição com namespaces isolados. O adaptador não faz esse isolamento automaticamente.

WordPress 7.1 com PHP 8.1.12/Illuminate 10.49.0: 28 verificações simples e 37 multisite aprovadas, sem diagnósticos. Evidência em docs/compatibility/wordpress-7.1-multisite.json. Também passaram 28/37 verificações em PHP 8.3.33 com Illuminate 13.30.1 carregado primeiro por outro autoloader. Veja docs/compatibility/wordpress-7.1-modern-multisite.json; isso não garante coexistência de versões incompatíveis de uma classe.

Preparar versões reproduzíveis

O gerador aceita uma versão SemVer exata, opcionalmente -rc.N. Sem argumento, mantém dev-main. Versões nomeadas anteriores ficam no índice; repetir uma versão é recusado. Dependências entre os pacotes FX ficam presas à mesma versão. A tag histórica v1.0.01 permanece intocada.

git fetch origin
php tools/package-repository.php C:/temporarios/fx-candidato https://github.com/Flavisnei/fxframework 1.1.0-rc.1

O destino deve ser novo e fora do checkout. O gerador usa apenas HEAD e cria packages.json e publish-plan.json; não publica sozinho. Revise o plano, publique refs e tags sem force e somente depois atualize o índice Composer. Uma versão candidata serve para homologação; a aprovação visual e do SMTP continua manual antes de declarar uma nova versão estável.

Instalar a candidata 1.1.0-rc.1

Os onze pacotes têm snapshots fixos com tags packages/NOME/v1.1.0-rc.1. No composer.json de uma aplicação nova, use o repositório abaixo e selecione somente os componentes necessários:

{
  "name": "minha/aplicacao",
  "minimum-stability": "RC",
  "prefer-stable": true,
  "repositories": [{"type":"composer","url":"https://raw.githubusercontent.com/Flavisnei/fxframework/main/docs/composer"}],
  "require": {"fxfavalessa/fx-core":"1.1.0-rc.1"}
}

Execute composer install --no-plugins --no-scripts. Para Admin com Artisan, selecione fx-admin e fx-console na mesma versão; as dependências FX transitivas ficam fixadas. É uma candidata de homologação, com revisão visual e SMTP ainda manuais. A versão do pacote Composer é independente do número interno do manifesto do módulo.

Atualização e retorno

Antes de atualizar, guarde composer.json, composer.lock, configuração e backup consistente do banco. Na homologação, selecione a versão exata dos pacotes, execute composer update com --with-all-dependencies --no-plugins --no-scripts e confira composer check-platform-reqs e os fluxos da aplicação. Versões RC exigem minimum-stability RC no consumidor; prefer-stable pode permanecer true.

Para retornar, restaure o manifesto e o lock anteriores e execute composer install --no-plugins --no-scripts. Isso restaura código e dependências, não reverte migrations ou dados. A instalação isolada de oito pacotes dev-main, atualização para 1.1.0-rc.1 e restauração dos oito snapshots passou com a mesma conta MariaDB, sem Eloquent ou Smarty; evidência em docs/compatibility/release-1.1.0-rc.1.json. Esta etapa não altera o schema; futuras migrations devem documentar compatibilidade e retorno antes da publicação. Se o Composer não encontrar uma versão, confira o índice e use composer show --all. Não apague banco ou rode migrations reversas sem um plano específico.
